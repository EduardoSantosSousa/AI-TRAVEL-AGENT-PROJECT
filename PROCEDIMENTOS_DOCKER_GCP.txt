PROCEDIMENTOS EXPLICADOS PARA DOCKER, KUBERNETES E GITHUB
Projeto: AI Travel Agent

Objetivo geral
--------------
Este documento explica como preparar a aplicacao para deploy usando:

1. GitHub para versionar o codigo.
2. Docker para empacotar backend e frontend em imagens.
3. Um container registry para armazenar as imagens.
4. Kubernetes para executar, escalar e expor a aplicacao.

A ideia principal e transformar a aplicacao em algo reproduzivel.
Em vez de depender da configuracao da sua maquina, criamos imagens Docker.
Em vez de subir processos manualmente, deixamos o Kubernetes controlar os containers.
Em vez de guardar codigo apenas localmente, usamos GitHub para historico, colaboracao e futuras automacoes.


1. ARQUITETURA DO PROJETO
-------------------------
Backend:
- Framework: FastAPI
- Arquivo principal: backend/main.py
- Objeto da aplicacao: app
- Comando local:
  python -m uvicorn backend.main:app --reload

Frontend:
- Framework: Vite com HTML/CSS/JavaScript
- Pasta: frontend
- Comando local:
  npm run dev

Variaveis de ambiente do backend:
- GROQ_API_KEY
- GOOGLE_MAPS_API_KEY

Por que isso importa?
---------------------
Antes de criar Dockerfile ou Kubernetes, precisamos entender como a aplicacao inicia.
O Dockerfile precisa saber qual comando roda o backend.
O Kubernetes precisa saber qual porta o container expoe.
O frontend precisa saber para qual URL enviar as requisicoes da API.

Neste projeto, o backend roda com Uvicorn na porta 8080 dentro do container.
O frontend sera buildado pelo Vite e servido pelo Nginx.


2. CUIDADOS IMPORTANTES ANTES DO DEPLOY
---------------------------------------
Hoje o frontend usa:

const API_BASE_URL = "http://127.0.0.1:8000";

Esse endereco funciona apenas na sua maquina.
Dentro do navegador de um usuario, 127.0.0.1 significa a maquina do proprio usuario, nao o container do backend.

Em producao, o frontend precisa chamar algo como:

https://api.seu-dominio.com

ou a URL publica do Ingress/LoadBalancer.

Tambem existe o CORS no backend.
Hoje o backend permite chamadas de:

http://localhost:5173

Em producao, sera necessario permitir o dominio real do frontend:

https://app.seu-dominio.com

Por que isso importa?
---------------------
Mesmo que backend e frontend estejam funcionando, o navegador pode bloquear a chamada se o CORS nao permitir a origem do frontend.
Esse e um erro muito comum em deploys de aplicacoes web.

4. CRIAR .gitignore
-------------------
Crie um arquivo chamado .gitignore na raiz:

venv/
__pycache__/
*.pyc
.env
logs/
frontend/node_modules/
frontend/dist/
AI_Travel_Agent.egg-info/
.pytest_cache/

Por que fazer isso?
-------------------
O GitHub deve guardar o codigo-fonte e os arquivos de configuracao necessarios.
Ele nao deve guardar:

- ambiente virtual Python;
- dependencias instaladas localmente;
- logs;
- arquivos de build;
- chaves de API;
- arquivos temporarios.

Isso deixa o repositorio menor, mais seguro e mais facil de reproduzir.


5. VERSIONAR O CODIGO COM GITHUB
--------------------------------
Na raiz do projeto:

git init
git status
git add .
git commit -m "Initial AI Travel Agent project"

Crie um repositorio no GitHub.

Depois conecte o repositorio remoto:

git remote add origin https://github.com/SEU_USUARIO/ai-travel-agent.git
git branch -M main
git push -u origin main

Fluxo recomendado para novas mudancas:

git checkout -b feature/docker-kubernetes-deploy

Depois de criar Dockerfiles e manifests:

git add .
git commit -m "Add Docker and Kubernetes deployment files"
git push -u origin feature/docker-kubernetes-deploy

Por que usar branches?
----------------------
A branch main deve representar uma versao estavel.
Quando voce cria uma branch feature, consegue trabalhar em mudancas sem quebrar a versao principal.
Depois, abre um Pull Request no GitHub para revisar as alteracoes antes de juntar na main.

Isso e importante em projetos profissionais porque cria historico, revisao e rastreabilidade.


6. CRIAR .dockerignore
----------------------
Crie um arquivo chamado .dockerignore na raiz:

venv
__pycache__
*.pyc
.env
logs
frontend/node_modules
frontend/dist
.git
.gitignore
AI_Travel_Agent.egg-info

Por que fazer isso?
-------------------
O Docker build envia arquivos para o contexto de build.
Se voce nao ignorar arquivos desnecessarios, a imagem pode ficar maior e o build mais lento.

Tambem evitamos copiar arquivos sensiveis, como .env, para dentro da imagem.
As variaveis secretas devem ser injetadas pelo Kubernetes, nao embutidas na imagem.


7. CRIAR DOCKERFILE DO BACKEND
------------------------------
Crie Dockerfile.backend na raiz:

FROM python:3.12-slim

WORKDIR /app

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY backend ./backend
COPY config ./config
COPY core ./core
COPY src ./src
COPY utils ./utils

EXPOSE 8080

CMD ["uvicorn", "backend.main:app", "--host", "0.0.0.0", "--port", "8080"]

Explicacao do Dockerfile
------------------------
FROM python:3.12-slim
Define a imagem base. Usamos Python 3.12 porque seu ambiente local usa Python 3.12.
A versao slim e menor que a imagem completa.

WORKDIR /app
Define a pasta de trabalho dentro do container.

ENV PYTHONDONTWRITEBYTECODE=1
Evita gerar arquivos .pyc dentro do container.

ENV PYTHONUNBUFFERED=1
Faz os logs aparecerem imediatamente no terminal/Kubernetes.

COPY requirements.txt .
Copia primeiro o requirements.txt.
Isso ajuda o cache do Docker: se suas dependencias nao mudarem, o Docker reaproveita essa camada.

RUN pip install --no-cache-dir -r requirements.txt
Instala as dependencias Python dentro da imagem.

COPY backend/config/core/src/utils
Copia o codigo da aplicacao.

EXPOSE 8080
Documenta que a aplicacao escuta na porta 8080.

CMD [...]
Comando que inicia o backend FastAPI usando Uvicorn.

Por que usamos 0.0.0.0?
-----------------------
Se usasse 127.0.0.1 dentro do container, a aplicacao ficaria acessivel apenas dentro do proprio container.
Com 0.0.0.0, ela aceita conexoes vindas de fora do container.


8. TESTAR BACKEND LOCALMENTE COM DOCKER
---------------------------------------
Na raiz do projeto:

docker build -f Dockerfile.backend -t ai-travel-backend:local .

docker run --rm -p 8080:8080 `
  -e GROQ_API_KEY="sua_chave_groq" `
  -e GOOGLE_MAPS_API_KEY="sua_chave_google" `
  ai-travel-backend:local

Teste:

http://localhost:8080/docs

Por que testar localmente?
--------------------------
Antes de mandar a imagem para o registry ou para Kubernetes, precisamos provar que ela funciona localmente.
Isso reduz muito o tempo de debug.

Se falhar aqui, o problema esta no Dockerfile, nas dependencias ou nas variaveis.
Se funcionar aqui e falhar no Kubernetes, o problema provavelmente esta nos manifests, secrets, rede ou configuracao do cluster.


9. PREPARAR O FRONTEND PARA URL DA API
--------------------------------------
Hoje o arquivo frontend/src/api/itineraryApi.js usa:

const API_BASE_URL = "http://127.0.0.1:8000";

Opcao recomendada:

const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || "http://127.0.0.1:8000";

Por que usar variavel de ambiente no frontend?
----------------------------------------------
Porque a URL do backend muda entre ambientes:

- local: http://127.0.0.1:8000
- staging: https://api-staging.seu-dominio.com
- producao: https://api.seu-dominio.com

Com variavel de ambiente, voce evita alterar codigo manualmente a cada deploy.

Atencao:
--------
Em apps Vite, variaveis expostas ao frontend precisam comecar com VITE_.
Exemplo:

VITE_API_BASE_URL=https://api.seu-dominio.com


10. CRIAR DOCKERFILE DO FRONTEND
--------------------------------
Crie frontend/nginx.conf:

server {
    listen 8080;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

Crie frontend/Dockerfile:

FROM node:22-alpine AS build

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

FROM nginx:alpine

COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html

EXPOSE 8080

CMD ["nginx", "-g", "daemon off;"]

Explicacao do Dockerfile do frontend
------------------------------------
Este Dockerfile tem dois estagios.

Primeiro estagio: build
- Usa Node.js.
- Instala dependencias.
- Executa npm run build.
- Gera arquivos estaticos na pasta dist.

Segundo estagio: runtime
- Usa Nginx.
- Copia apenas os arquivos finais da pasta dist.
- Serve HTML, CSS e JS.

Por que dois estagios?
----------------------
Porque o Node.js so e necessario para compilar o frontend.
Em producao, quem serve o site e o Nginx.
Assim a imagem final fica menor, mais simples e com menos superficie de ataque.

Por que Nginx escutando 8080?
-----------------------------
Em Kubernetes, podemos usar qualquer porta, mas manter 8080 cria padrao entre backend e frontend.
O Service depois encaminha trafego da porta 80 para a porta 8080 do container.

12. PUBLICAR IMAGENS EM UM REGISTRY
-----------------------------------
Kubernetes nao usa diretamente a imagem que esta apenas na sua maquina.
O cluster precisa baixar a imagem de um registry.

Opcoes comuns:
- Docker Hub
- Google Artifact Registry
- GitHub Container Registry

Exemplo usando Google Artifact Registry:

gcloud auth login
gcloud config set project SEU_PROJECT_ID

gcloud services enable artifactregistry.googleapis.com

gcloud artifacts repositories create ai-travel-repo `
  --repository-format=docker `
  --location=us-central1 `
  --description="AI Travel Agent Docker images"

gcloud auth configure-docker us-central1-docker.pkg.dev

Build e push do backend:

docker build -f Dockerfile.backend `
  -t us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/backend:v1 .

docker push us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/backend:v1

Build e push do frontend:

docker build `
  -t us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/frontend:v1 `
  ./frontend

docker push us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/frontend:v1

Por que usar tags versionadas?
------------------------------
Evite depender apenas de latest.
Tags como v1, v2 ou v1.0.0 deixam claro qual versao esta rodando.

Isso facilita rollback.
Se a v2 quebrar, voce pode voltar para v1.


13. CRIAR PASTA K8S
-------------------
Na raiz do projeto:

mkdir k8s

Por que criar uma pasta k8s?
----------------------------
Manifests Kubernetes sao arquivos declarativos.
Eles descrevem o estado desejado da aplicacao.

Exemplo:
- quero 2 replicas do backend;
- quero um Service para expor o backend internamente;
- quero um Secret com as chaves;
- quero um Ingress para receber trafego externo.

Guardar isso em k8s/ deixa a infraestrutura versionada junto com a aplicacao.


14. CRIAR SECRET DO BACKEND
---------------------------
Crie k8s/backend-secret.yaml:

apiVersion: v1
kind: Secret
metadata:
  name: ai-travel-backend-secret
type: Opaque
stringData:
  GROQ_API_KEY: "trocar_antes_do_deploy"
  GOOGLE_MAPS_API_KEY: "trocar_antes_do_deploy"

Por que usar Secret?
--------------------
O backend precisa de chaves para chamar Groq e Google Maps.
Essas chaves nao devem ficar dentro do codigo nem da imagem Docker.

O Secret permite injetar esses valores no Pod como variaveis de ambiente.

Atencao importante:
-------------------
Nao envie secrets reais para o GitHub.
Para estudar e versionar, crie um arquivo:

k8s/backend-secret.example.yaml

E crie o secret real por comando:

kubectl create secret generic ai-travel-backend-secret `
  --from-literal=GROQ_API_KEY="sua_chave_groq" `
  --from-literal=GOOGLE_MAPS_API_KEY="sua_chave_google"


15. CRIAR DEPLOYMENT DO BACKEND
-------------------------------
Crie k8s/backend-deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-travel-backend
  labels:
    app: ai-travel-backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ai-travel-backend
  template:
    metadata:
      labels:
        app: ai-travel-backend
    spec:
      containers:
        - name: backend
          image: us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/backend:v1
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          envFrom:
            - secretRef:
                name: ai-travel-backend-secret
          readinessProbe:
            httpGet:
              path: /docs
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /docs
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 30
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
            limits:
              cpu: "1"
              memory: "1Gi"

Explicacao do Deployment
------------------------
Deployment e o recurso que diz ao Kubernetes como executar sua aplicacao.

replicas: 2
Pede duas copias do backend.
Se um Pod cair, o Kubernetes cria outro.

selector/matchLabels
Diz quais Pods pertencem a esse Deployment.

image
Define qual imagem Docker sera usada.

ports/containerPort
Informa que o container escuta na porta 8080.

envFrom/secretRef
Carrega variaveis de ambiente a partir do Secret.

readinessProbe
Diz quando o Pod esta pronto para receber trafego.

livenessProbe
Diz se o container ainda esta saudavel.
Se falhar repetidamente, o Kubernetes reinicia o container.

resources
Define CPU e memoria solicitados e limites maximos.
Isso ajuda o cluster a agendar Pods e evita consumo descontrolado.


16. CRIAR SERVICE DO BACKEND
----------------------------
Crie k8s/backend-service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: ai-travel-backend-service
spec:
  selector:
    app: ai-travel-backend
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
  type: ClusterIP

Por que Service?
----------------
Pods sao descartaveis.
Eles podem ser recriados com outro IP.

O Service cria um endereco estavel dentro do cluster.
Ele encaminha trafego para os Pods que possuem o label app: ai-travel-backend.

port: 80
Porta exposta pelo Service.

targetPort: 8080
Porta real dentro do container.

type: ClusterIP
Significa que o Service e acessivel internamente no cluster.
O acesso externo sera feito pelo Ingress.


17. CRIAR DEPLOYMENT DO FRONTEND
--------------------------------
Crie k8s/frontend-deployment.yaml:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: ai-travel-frontend
  labels:
    app: ai-travel-frontend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: ai-travel-frontend
  template:
    metadata:
      labels:
        app: ai-travel-frontend
    spec:
      containers:
        - name: frontend
          image: us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/frontend:v1
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /
              port: 8080
            initialDelaySeconds: 20
            periodSeconds: 30
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi"

Por que o frontend tambem usa Deployment?
-----------------------------------------
Mesmo sendo arquivos estaticos, o frontend esta rodando dentro de um container Nginx.
O Kubernetes precisa controlar esse container tambem.

Com replicas: 2, voce tem mais disponibilidade.
Se um Pod do frontend cair, outro continua servindo.


18. CRIAR SERVICE DO FRONTEND
-----------------------------
Crie k8s/frontend-service.yaml:

apiVersion: v1
kind: Service
metadata:
  name: ai-travel-frontend-service
spec:
  selector:
    app: ai-travel-frontend
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
  type: ClusterIP

Por que Service no frontend?
----------------------------
Pelo mesmo motivo do backend.
O Ingress nao deve apontar diretamente para Pods.
Ele aponta para um Service, e o Service distribui trafego para os Pods corretos.


19. CRIAR INGRESS
-----------------
Crie k8s/ingress.yaml:

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: ai-travel-ingress
  annotations:
    kubernetes.io/ingress.class: "gce"
spec:
  rules:
    - host: app.seu-dominio.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: ai-travel-frontend-service
                port:
                  number: 80
    - host: api.seu-dominio.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: ai-travel-backend-service
                port:
                  number: 80

Por que usar Ingress?
---------------------
Service ClusterIP e interno.
Ingress e o recurso que recebe trafego externo HTTP/HTTPS e direciona para os Services.

Neste exemplo:
- app.seu-dominio.com vai para o frontend;
- api.seu-dominio.com vai para o backend.

Isso deixa a arquitetura mais organizada.
O frontend e a API ficam separados, mas acessiveis por dominios claros.

Observacao sobre HTTPS
----------------------
Em producao, use HTTPS.
No GKE, voce pode configurar ManagedCertificate ou outro controlador de Ingress.
Sem HTTPS, navegadores podem bloquear recursos e os usuarios ficam menos protegidos.


20. APLICAR ARQUIVOS NO KUBERNETES
----------------------------------
Conecte no cluster.

Exemplo GKE:

gcloud container clusters get-credentials SEU_CLUSTER `
  --region us-central1 `
  --project SEU_PROJECT_ID

Aplicar manifests:

kubectl apply -f k8s/backend-secret.yaml
kubectl apply -f k8s/backend-deployment.yaml
kubectl apply -f k8s/backend-service.yaml
kubectl apply -f k8s/frontend-deployment.yaml

Tambem pode aplicar tudo:

Por que usar kubectl apply?
---------------------------
O apply envia ao Kubernetes o estado desejado.
Se o recurso nao existir, ele cria.
Se ja existir, ele atualiza.

Isso combina bem com infraestrutura como codigo.
Os arquivos YAML viram a fonte da verdade.


21. VERIFICAR O DEPLOY
----------------------
Comandos principais:

kubectl get pods
kubectl get deployments
kubectl get services
kubectl get ingress

Ver detalhes de um Pod com problema:

kubectl describe pod NOME_DO_POD

Ver logs do backend:

kubectl logs deployment/ai-travel-backend

Ver logs do frontend:

kubectl logs deployment/ai-travel-frontend

Por que esses comandos importam?
--------------------------------
Eles ajudam a descobrir onde esta o problema:

- Pod nao sobe: problema de imagem, comando, dependencia ou secret.
- Pod sobe mas nao fica Ready: problema na readinessProbe.
- Service nao responde: problema de selector/labels/porta.
- Ingress nao responde: problema no Ingress, dominio, DNS ou LoadBalancer.


22. AJUSTAR CORS DO BACKEND
---------------------------
No arquivo backend/main.py, ajuste:

allow_origins=[
    "http://localhost:5173",
    "https://app.seu-dominio.com",
]

Por que isso precisa ser feito?
-------------------------------
O CORS e uma protecao do navegador.
Ele impede que qualquer site aleatorio chame sua API pelo browser.

Quando seu frontend estiver em https://app.seu-dominio.com e chamar https://api.seu-dominio.com, o backend precisa permitir essa origem.

Depois do ajuste:

git add backend/main.py
git commit -m "Configure production CORS origin"
git push

Depois:

1. Criar nova imagem do backend.
2. Fazer push para o registry.
3. Atualizar a tag no backend-deployment.yaml.
4. Aplicar novamente no Kubernetes.


23. ATUALIZAR DEPLOYMENT COM NOVA VERSAO
----------------------------------------
Quando criar uma nova versao:

docker build -f Dockerfile.backend `
  -t us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/backend:v2 .

docker push us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/backend:v2

Atualize o YAML:

image: us-central1-docker.pkg.dev/SEU_PROJECT_ID/ai-travel-repo/backend:v2

Aplique:

kubectl apply -f k8s/backend-deployment.yaml

Verifique rollout:

kubectl rollout status deployment/ai-travel-backend

Rollback se necessario:

kubectl rollout undo deployment/ai-travel-backend

Por que isso e importante?
--------------------------
Kubernetes permite atualizar a aplicacao gradualmente.
Ele derruba Pods antigos e sobe Pods novos.

Se algo der errado, voce pode voltar para a versao anterior com rollout undo.
Esse controle e uma das grandes vantagens de usar Kubernetes.

26. RESUMO MENTAL DO FLUXO
--------------------------
1. Codigo fica no GitHub.
2. Dockerfile transforma codigo em imagem.
3. Registry armazena a imagem.
4. Kubernetes baixa a imagem e cria Pods.
5. Deployment controla replicas e atualizacoes.
6. Service cria endereco estavel para os Pods.
7. Ingress expoe frontend e backend para a internet.
8. Secret injeta chaves sem colocar segredos no codigo.


27. RESUMO RAPIDO DE COMANDOS

Versionamento:

git init
git add .
git commit -m "Initial commit"
git remote add origin https://github.com/SEU_USUARIO/ai-travel-agent.git
git push -u origin main

Backend Docker:

docker build -f Dockerfile.backend -t ai-travel-backend:local .
docker run --rm -p 8080:8080 -e GROQ_API_KEY="..." -e GOOGLE_MAPS_API_KEY="..." ai-travel-backend:local

Frontend Docker:

docker build -t ai-travel-frontend:local ./frontend
docker run --rm -p 5173:8080 ai-travel-frontend:local

Kubernetes:

kubectl apply -f k8s/
kubectl get pods
kubectl get services
kubectl get ingress
